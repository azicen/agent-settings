# Craftsmanship — 语言无关的代码编写原则

## 适用范围

本 skill 覆盖语言无关的通用代码编写原则，适用于 agent 编写新代码、修改已有代码或进行代码重构时使用。

**不覆盖**以下内容——这些由语言 / 框架专用 skill 负责：
- 语言的错误处理惯用法（`%w`、`from e`、`?` 等）
- 语言的并发惯用法（goroutine、async/await、Actor 等）
- 语言的资源管理惯用法（defer、with、RAII 等）
- 框架的分层约定和项目目录结构
- 语言的反模式清单和工具链推荐

---

## 核心哲学

这三条是所有决策的最终裁判。

### 1. 先正确，再整洁

不为了代码漂亮省略必要的边界处理、错误处理、安全约束。如果整洁和正确冲突，选择正确。

### 2. 减少认知负担，而不是减少行数

删减的对象是不必要的分支、嵌套、抽象、状态、魔法写法、解释成本——不是字符数。简洁不是更短，是让人脑中需要补全的信息更少。

### 3. 一致性优先于局部最优

遵循已有项目的写法、结构、命名、错误处理方式。一致的普通写法胜过孤立的聪明写法。如果没有项目风格可循，选择最朴素直接的写法。

---

## 决策锚点

当两条原则互相冲突时，按以下优先级裁决：

| 优先 | 维度 | 判断问题 |
|------|------|---------|
| 0 | **正确性** | 代码是否做了该做的事？ |
| 1 | **可读性** | 新来的同事能立即理解吗？ |
| 2 | **可调试性** | 出了 bug 能快速定位吗？ |
| 3 | **内聚性** | 需求变了要动几个地方？ |

## 刚性约束

以下规则必须遵守，违反即为缺陷。每条附带 bad/good 对比，伪代码保持语言无关。

### 4. 信任边界处校验输入，内部依赖清晰契约

来自外部的数据（请求、文件、用户输入、第三方返回值）进入系统时必须校验。同一进程内的内部调用信任调用者已完成校验。

```
// bad — 不做校验直接处理外部输入
handle(externalInput)

// good — 在信任边界处校验
if invalid(externalInput) { return err }
handle(externalInput)
```

### 5. 错误在传播过程中不丢失定位所需的上下文

应有"在哪失败、做什么失败、为什么失败"。不吞错误，不丢弃原因，不把所有错误变成同一种。具体包装层级由语言惯用法决定。

```
// bad — 跨语义边界返回时，上层无法知道哪个操作失败
return err

// good — 携带操作上下文
return wrap(err, "charging order %s", orderID)
```

### 6. 资源生命周期有明确的边界和清理机制

打开→关闭，建立→释放，启动→可终止。资源的创建方和销毁方应为同一个作用域。

```
// bad — 循环内获取资源，退出后才释放
for item := range items {
    resource := acquire()
    process(item, resource)
}
closeAll()

// good — 每个资源的作用域和清理时机明确
for item := range items {
    resource := acquire()
    process(item, resource)
    resource.close()
}
```

### 7. 短路失败路径，保持主流程线性可读

异常状态尽早退出，不让深层嵌套掩盖失败点。主流程沿左侧对齐。

```
// bad — 深层嵌套掩盖主流程
if valid {
    if allowed {
        if notExpired {
            doWork()
        }
    }
}

// good — 失败路径提前退出
if !valid     { return }
if !allowed   { return }
if expired    { return }
doWork()
```

### 8. 每个处理步骤只有一个职责，步骤间数据流显式可追踪

不在校验里做计算，不在计算里做持久化。无论"步骤"是函数、operator 还是 pipeline stage，数据流应清晰可追踪。

每个函数可用一句话描述职责——如果需要用"并且"连接，考虑拆分。但如果拆分后需要理解多个子函数的编排才能理解整体流程，保持合并。

```
// bad — 交错执行：循环内既读、又验、又写
for row := readRow(file) {
    if validate(row) { insert(row) }
}

// good — 分阶段处理，各步骤职责独立
stream := readRowStream(file)
validStream := filter(stream, validate)
batchInsert(validStream, batchSize)
```

### 9. 让意图显式——通过命名、类型、结构让代码自解释

命名表达业务含义，让读者立即知道"是什么"和"为什么存在"。避免 `data`、`info`、`tmp`、`manager`、`helper` 等空泛词。

```
// bad — 命名不表达业务含义
items := fetch()
result := transform(items)

// good — 命名即文档
invoiceItems := fetchOrderItems(orderID)
validItems := filterExpired(invoiceItems)
```

### 10. 空值 / 缺失值必须被类型系统或显式检查捕获，不允许隐式传播

空值应在边界处处理为有意义的错误或默认值，不向内部逻辑渗透。如果语言支持 Optional 类型或非空类型，优先使用之为编译期保障——比运行时检查更可靠。

```
// bad — 签名上的空值语义含糊，内部到处防御
func send(user *User) { // user 可能是 null
    if user == null { return }
    // ... 每个函数都要猜和防
}

// good — 用 Optional 把空值可能性提升到类型签名上
func send(user Optional[User]) {
    if !user.hasValue() { return }
    process(user.value()) // 此后不会为 null
}
```

### 11. 外部资源获取必须有显式上限

内存分配、连接数、文件大小、请求体、队列深度——所有从外部消耗的资源不允许无界增长。上限应显式编码，不依赖"默认无限制"。

```
// bad — 无上限约束，来多少处理多少
for file := range uploads {
    store(file)
}

// good — 显式上限保护
if count(uploads) > maxFileCount { return errTooMany }
for file := range uploads {
    if file.size > maxFileSize { return errTooLarge }
    store(file)
}
```

### 12. 日志有级别、有上下文、无敏感数据

Error 日志必须有足够上下文定位问题。敏感数据（密码、token、身份信息、会话标识）不出现在日志中。循环内不打大量日志。

```
// bad — 无上下文无法定位 + 敏感数据泄露
log("operation failed")
log("user login: password=%s", password)

// good — 携带定位信息，敏感数据不输出
log("order payment failed", "orderID", id, "reason", err)
log("user login attempt", "userID", uid, "fromIP", ip)
```

## 柔性建议

以下规则应倾向遵守。在有合理理由时可偏离，但建议在注释或 commit message 中说明原因。柔性建议不配 bad/good 示例，避免教条化。

### 13. 偏好不可变数据，可变状态限制在最小必要范围

数据创建后尽可能保持不变，需要修改时创建新副本。可变状态只在跨多次操作共享且性能敏感时使用。高频率写入热路径上，可变性 + 明确所有权可接受。

### 14. 避免跨并发边界的共享可变状态

如果必须有，用明确的同步机制保护，锁范围尽量小。优先级：无共享 > 消息传递 > 有保护的共享 > 无保护的共享。

### 15. 抽象已经发生的真实变化，不抽象想象中的未来

存在两个及以上真实实现、或变化方向已明确时才引入抽象。领域边界（如数据访问接口）可以适当提前——尤其是当框架约定要求时。

### 16. 允许少量重复，警惕过早 DRY

两次重复可接受，三次再考虑抽象。消除重复前先确认：这两处会因为同样的原因同时变化吗？如果答案是不确定，保留重复优于错误抽象。

### 17. 可独立测试的逻辑不依赖 IO，IO 范围尽量小

核心业务逻辑写成可单元测试的无副作用函数，IO 操作集中在边界层。时间、外部服务、文件系统等通过接口或参数注入。

### 18. 超时和取消信号由调用者传入，不硬编码

任何执行外部 I/O 的操作必须接受并尊重超时。超时值不在函数内部写死，由调用者根据上下文决定。

### 19. 可重试操作必须幂等，或显式标注非幂等

涉及外部副作用的操作（网络调用、消息处理、分布式请求），调用方需要知道重复执行是否安全。幂等性不是默认假设，是显式设计决策。

### 20. 注释解释"为什么"，不重复"是什么"

代码说明做什么，命名说明是什么，注释说明原因、约束、坑点和历史背景。如果代码清晰到不需要注释，那就不写。但业务背景、并发约束、外部系统的异常行为必须注释。

### 21. 依赖从具体指向抽象，从外层指向内层

核心业务逻辑不依赖框架和基础设施细节。接口定义在消费方，不定义在实现方。不稳定的模块依赖稳定的模块，不反过来。

## 应用方法

1. **编写新代码**：先满足核心哲学（1-3），再逐条对照刚性约束（4-12）。
2. **修改已有代码**：先观察项目已有风格（第 3 条），新代码与之保持一致。不因个人偏好引入不同写法。
3. **原则冲突时**：用决策锚点裁决——正确性 > 可读性 > 可调试性 > 内聚性。
4. **不确定是否应该抽象 / 拆分 / 消除重复时**：选择让代码更容易删除的方案。写完后再问自己：如果明天要删掉这段功能，改动会涉及多少地方？
5. **重构时**：每次重构只有一个方向（只改名、只拆函数、只改结构），不混在一起。确保重构前后行为不变。
